# PhoneAgent 设计复盘与面试指南

这份文档不是背诵稿。它用于把代码、设计约束、测试证据和项目边界连起来，帮助项目作者
独立解释每个重要决定。

## 30 秒项目介绍

PhoneAgent 是一个运行在电脑端、通过 ADB 操作真实 Android 设备的视觉语言智能体研究与
评测运行时。它把一次自然语言任务收敛为可审计循环：获取可信截图、让视觉模型规划、严格
解析唯一终端动作、执行 ADB 命令、验证可观察结果，并在失败时进行有界恢复。项目重点不是
支持最多应用，而是让动作为什么执行、为什么失败、是否恢复以及最终结果是否可信都有证据。

## 一条请求如何执行

```text
用户任务
  → 首次可信观察
  → 构造模型上下文
  → 流式模型响应
  → 严格动作协议
  → 敏感操作策略
  → ADB 原子动作
  → 结果验证
  → 成功进入下一步 / 失败进入有界恢复
  → 事件流与 trajectory
```

讲解时应从边界和不变量入手，而不是逐个介绍类名：

- `AgentState.phase` 是实时阶段的唯一来源；
- trajectory 事件流是历史事实的唯一来源；
- 模型输出是不可信输入，只有通过协议解析和白名单校验的动作才能进入执行层；
- 设备命令成功不等于任务语义成功；
- 高风险坐标动作失败后不能盲目重放；
- 取消只能在安全检查点阻止后续动作，不能假装撤销已经下发的原子 ADB 命令。

## 四个最值得讲的复杂问题

### 1. 如何约束模型输出

问题不是“能否从文本里找到一个动作”，而是“哪一段文本拥有执行权”。PhoneAgent 只接受
响应末尾唯一且完整的 `do(...)` 或 `finish(...)`，前面的内容仅作为推理记录。协议层使用
AST 解析结构，并只对字面量调用 `ast.literal_eval`；它不会对模型文本执行 `eval`。

这个决定牺牲了对模糊输出的宽容度，换来明确的执行边界、可复现失败和更简单的安全审计。
协议错误不会被字符串修补，而会成为结构化失败并重新规划。

### 2. 如何判断动作真的有效

ADB 返回码只能证明命令被系统接受。例如点击命令成功，不代表点中了正确按钮；启动命令
成功，也不代表目标包进入前台。因此验证层区分：

- command success：设备命令是否成功；
- observable effect：截图、前台包或系统窗口是否发生预期变化；
- semantic effect：Android 是否提供足够的确定性证据证明动作语义。

无法确定语义时保持 `None`，而不是伪造成功。系统面板动作会检查 WindowManager 证据；
直接启动会核对前台包名；普通坐标动作通常只能证明可观察变化。

### 3. 如何恢复而不制造更大风险

恢复策略被限制为重新规划、重新观察、安全动作重试、人工接管和终止。只有 `Launch`、
`Wait`、`Home` 可以在非敏感情况下获得一次动作重试。`Tap`、`Type`、`Swipe`、`Back`、
`Double Tap` 和 `Long Press` 不会自动重放，因为重复点击、发送或返回可能产生不可逆副作用。

恢复同时受单次失败预算和整个任务预算限制。一次恢复成功后会重置连续失败计数，使预算描述
的是当前失败 episode，而不是永久惩罚此前已经解决的问题。

### 4. 如何处理 Web Console 的并发

Web Console 复用一个通过预检的 Agent，但同时只允许一个任务。旧实现的风险是：前一个
后台线程已经进入终态，但延迟回调仍可能修改下一个任务。当前实现给每代任务绑定 ContextVar
标识，事件、提示和备注回调必须匹配当前任务 ID；前一工作线程完成清理后才允许下一任务
启动。测试通过事件同步稳定复现旧回调晚到的竞态，不依赖碰运气式短延时。

## v0.2.0 重构为什么不是重写

重构冻结了公开 API、CLI、环境变量、Web 路由、动作协议和 trajectory schema。状态与事件
所有权仍保留在 `PhoneAgent`，先拆纯逻辑和阶段边界，再删除已证明无人使用的私有同步包装。
这样可以降低局部复杂度，同时避免引入两个生命周期事实来源。

可量化变化：

| 边界 | v0.1.4 | v0.2.0 重构分支 |
| --- | ---: | ---: |
| `_execute_step_async` | 394 行 | 29 行协调器 |
| 动作处理模块 | 760 行 | 369 行，协议与策略已拆出 |
| 模型 `_request_once` 最大实现 | 157 行 | 74 行，共享响应状态 |
| Web `app.js` | 1070 行 | 704 行，拆出 4 个原生模块 |

行数不是最终目标。真正收益是每个故障能够被定位到观察、协议、策略、执行、验证或恢复阶段，
并且每个边界可以独立进行故障注入。

## 面试时可以展示的证据

- 单元和集成式测试覆盖同步/异步入口、事件顺序、取消、安全恢复和 Web 竞态；
- 注入截图超时、ADB 断连、协议截断、前台包不匹配和旧任务延迟回调；
- 核心协议、状态、验证、恢复和轨迹模块保持至少 80% 分支覆盖率；
- release check 验证 lint、测试、JavaScript、构建、校验和以及 wheel 干净安装；
- `phoneagent-eval` 将 runtime success 与外部标注的 task success 分开；
- 真机矩阵记录设备、ROM、模型、commit、失败码和脱敏轨迹。

任何成功率都应带任务集合、初始状态、设备、模型、重复次数和外部判定方法。不要把
`finish(success=True)`、屏幕变化或 ADB 返回码包装成端到端任务成功率。

## 常见追问

### 为什么不用 UI XML 或无障碍树？

当前目标是研究基于视觉观察的通用 GUI Agent，并覆盖无法稳定获得结构树的界面。代价是坐标
动作的语义验证较弱，因此项目必须保留截图证据、前台包信息、有界恢复和人工判定。未来可以
把结构树作为额外观察源，但不能让它成为另一套独立状态机。

### 为什么不一次让模型输出多个动作？

设备状态会在每个动作后改变。单动作闭环可以重新观察和验证，降低基于过期画面连续操作的
风险，也使每一步轨迹更容易审计。代价是请求次数和延迟增加。

### 为什么不用复杂工作流框架？

当前控制流只有一个线性循环和五种恢复决策。引入框架会增加隐式状态、序列化和调试成本，
但没有解决核心的不可信模型输出与设备验证问题。等到确实出现并行子任务、持久化恢复或多
Agent 协作需求时再评估。

### 项目最大的不足是什么？

视觉变化不能独立证明坐标目标的语义正确，受保护页面不可观察，不同 ROM 的系统行为存在
差异，而且完整任务结束仍由规划模型提出。项目通过诚实区分证据等级和外部任务标注来管理
这些限制，而不是宣称已经消除它们。

## 自测要求

在把项目写进简历前，应能不看代码回答以下问题，并能指出对应测试或 trajectory 证据：

1. 模型输出从字符串到 ADB 命令经过哪些信任边界？
2. command success、observable effect 和 semantic effect 有什么区别？
3. 为什么 `Launch` 可以重试而 `Tap` 不可以？
4. 取消发生在模型流、Wait 和原子 ADB 命令期间时分别会怎样？
5. 为什么 state snapshot 和 event stream 不能互相替代？
6. Web 旧任务回调为什么可能污染新任务，当前如何证明不会？
7. runtime success 为什么不能作为 task success？
8. v0.2.0 重构保持了哪些兼容契约，又主动拒绝了哪些功能扩张？
